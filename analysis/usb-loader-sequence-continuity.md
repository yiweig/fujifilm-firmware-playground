# USB loader sequence continuity: refresh does not supply the next UI state

Date: 2026-11-01. Offline static analysis and ARM emulation only. No camera
commands, USB access or card changes. Official 2.00 main-image SHA-256:
`80350bd2bc37b4ce985742ff85a747f7c7ad1ed9be401534ba57ac3262f1d923`.
Runtime base `0x40000000`, little-endian ARMv7.

## Finding

The proposed RAM-staging/refresh/USB-event sequence is **not established as a
continuous loader-entry route**. The alternate refresh returns with UI state
`0x0001`. Supplying the USB event in that actual resulting state takes a
charging/status-handling branch, rather than directly selecting mode 4.

The earlier successful loader test supplied UI state `0x8000`. A transition
between these states was an explicit missing assumption, not demonstrated
camera behavior. This follow-up tests without supplying that transition.
It does not rule out a later asynchronous route to loader mode; that route
remains untraced.

## Continuous event test

The extended [emulator script](scripts/ReproduceTemporaryUsbSetting.java) keeps
the same machine after the full alternate refresh. At that point:

- synthetic cold-data RAM still contains the staged USB-setting byte;
- the cached USB selection flag is zero;
- UI state is `0x0001`.

It delivers `0xf0000044` through `0x404db31c` without replacing the UI state.
The dispatcher selects group-zero handler `0x404d51b0`. Comparisons at
`0x404d51d8..0x404d51f0` derive event `0xf0000044` from a literal and branch
to `0x404d54c4`:

```text
delay helper 0x4006a074(3, 300)
  -> USB-presence getter 0x40123d44
     zero: return
     nonzero: 0x401250e4 (leaf returns zero)
       -> status classifier 0x40124b08
          nonzero: return
          zero: 0x40124eec(0)
             -> 0x40124b74(0), charging-control boundary
```

The delay is simulated; the report does not infer its wall-clock units.
The presence getter's original instructions read bit 0 of MMIO byte
`0x1000517a`, supplied synthetically. The status classifier reads byte
`0x40e7ae40` and returns nonzero for values 1 or 2. Status meanings beyond
this predicate are not assigned here.

Two new controls passed:

| Synthetic input | Observed result |
| --- | --- |
| USB-presence bit 1, status byte 0 | Reaches `0x40124b74` with argument 0; stops before executing it. UI state 1, cached flag zero and all staged cold-data RAM remain unchanged. |
| USB-presence bit 0 | Returns before the charging-control boundary; no loader setter reached. |

The script does not simulate `0x40124b74` as an innocuous successful return:
it stops there. Its branch strings are `Charge Disable...` / `Charge Enable...`;
the shared tail calls peripheral helpers `0x40043220` and `0x40043318`.
The surrounding wrapper also references `ledId:%d` through `0x40124e94`.
This is evidence for charging/status/indicator handling, not for a jump to
the application RAM loader. No claim is made about every effect or future
event generated by the lower hardware operations.

The first expanded emulator run stopped at the previously unadmitted delay
helper. Its arguments and subsequent original instructions were inspected;
only that exact delay was added as a simulated return. Unexpected callees
continue to stop the test. Final output contains nine passing assertions,
including the earlier staging, restore, full-refresh and prerequisite controls:
[`output/temporary-usb-setting-continuity.txt`](output/temporary-usb-setting-continuity.txt).

## Cached USB state differs from raw presence

The earlier group-`0x8000` experiment supplied getter `0x40123bf8`. That
getter extracts bit 5 from cached runtime byte `0x40e7ab8c`; it does not read
the physical-presence register itself. This follow-up executes separate raw
presence getter `0x40123d44` against synthetic MMIO.

These values may correlate on a real camera, but supplying them independently
does not reproduce physical connection detection, its timing, charging
classification, or the events required to enter the connected UI group.

## Entry into 0x0301 remains unresolved

The prior search of 216 Ghidra write references to UI state was widened to
160-byte instruction windows. The nearest three simple source-register
definitions were inspected for each store. Immediate and PC-literal candidates
did not yield a qualified direct assignment of `0x0301` to this field.

Several dynamic stores restore a halfword from another runtime object instead
of creating a new state value. For example, `0x405330cc`, `0x40533368` and
`0x405333b0` copy saved UI state, while `0x405c9bd8` restores a halfword from
`0x413d3c90`. Their presence does not explain where an initial `0x0301` comes
from or whether an ordinary control sequence can produce it.

The local source-definition inventory is
`/private/tmp/ui-state-store-definitions.txt`, based on the reference export
`/private/tmp/usb-refresh-state-writers.txt`. This is bounded backward
inspection, not whole-program symbolic execution. It does not resolve
all register aliases, control flow, computed/block writes or earlier stages.
No absence-of-reachability claim is made. The existing no-op hooks around the
alternate path also make generic vendor help/text insufficient evidence of
retail activation on this build.

## Practical consequence

The evidence currently establishes three separate facts:

1. A factory callback can stage the setting in shared RAM.
2. A conditional UI handler can refresh the cached flag while avoiding the
   previously identified RTC cleanup, given supplied prerequisites and
   simulated display operations.
3. The loader is selectable by a USB event in certain connected UI contexts.

It does **not** yet connect them into a safe real-camera sequence. The remaining
questions are an actual producer of `0x0301`, its effect on staged RAM, and the
connection/status events after refresh. Pending callbacks, resource readiness,
later saves and restoration after a real USB handoff remain unqualified.

No live write, setting change, firmware flash or recovery test follows from
this result. Independent recovery before the main application is still a
separate missing requirement.

```sh
GHIDRA_PROJECT_DIR=/private/tmp/fuji-ghidra-v7 GHIDRA_PROJECT_NAME=FujiV7 \
  bash analysis/run-ghidra.sh -process firmware-main.bin -noanalysis \
  -postScript ReproduceTemporaryUsbSetting.java /private/tmp/temporary-usb-setting-continuity.txt
```

Existing local Ghidra 12.1.4 ARMv7 state was reused after the recorded REA
raw-image mapping issue. No fresh REA evidence or camera runtime observation
is claimed.

original charge-control path with modeled peripheral and indicator APIs. It
returns without a direct UI transition or loader selection, preserving the
staged setting; asynchronous hardware behavior remains unqualified.
